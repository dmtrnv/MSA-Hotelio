### <a name="_qmphm5d6rvi3"></a>**Решение**
Диаграмма контейнеров

Диаграмма развертывания
![Deployment](ADR-000-deployment.png)

Текущий монолит содержит модули `BookingService`, `UserService`, `HotelService`, `PromoCodeService` и `ReviewService`. Все они являются внутренними компонентами одного приложения и используют общую PostgreSQL БД.
В целевом состоянии каждый модуль становится отдельным сервисом (единица развертывания) и имеет собственную БД.

API Gateway и GraphQL BFF рассматриваются как разные уровни:
Задачи API Gateway: TLS termination, routing, authentication, rate limiting, CORS, request limits, correlation/request ID.
Задачи GraphQL BFF: агрегация данных нескольких сервисов, получение только необходимых полей, адаптация API под разные frontend клиенты.

На целевом этапе сервисы работают через service mesh.
Используются:
- service discovery
- mTLS
- timeout/retry policies
- circuit breaking
- traffic splitting
- canary releases
- observability
- automated rollouts

Для каждого сервиса обязательны трейсы, сбор метрик и логов.
Трейс должен сохраняться при прохождении запроса через Gateway/BFF и несколько сервисов.

Предлагается выполнение миграции поэтапно:
```text
Клиент
  |
  v
Gateway
  |
  v
 BFF
  |
  +----> Новый сервис
  |
  +----> Монолит
```
Сначала новый сервис получает небольшой процент трафика, затем доля постепенно увеличивается. После стабилизации трафик полностью переключается на новый сервис и из монолита удаляется функционал, вынесенный в этот сервис.

Предварительный план выноса сервисов:
1. Hotels
2. Users
3. Reviews
4. Promo
5. Booking

### <a name="_bjrr7veeh80c"></a>**Альтернативы**
#### 1. Сохранить монолит
Плюсы:
- минимальная инфраструктурная сложность;
- нет межсервисных сетевых вызовов.
Минусы:
- сохраняются проблемы независимого масштабирования;
- изменения требуют работы с общей кодовой базой;
- сохраняется единая БД.

#### 2. Переписать все разом на микросервисы
Основной недостаток - высокий migration risk и необходимость одномоментно решить все вопросы интеграции, данных, деплоя и отката.

**Сравнение решений**

| Критерий | Сохранить монолит | Переписать всё разом | Strangler Fig + Gateway + GraphQL BFF |
| :- | :- | :- | :- |
| Независимое развёртывание и масштабирование | ❌ Модули остаются в одном процессе — масштабируется только приложение целиком | ✅ Каждый сервис деплоится и масштабируется независимо с первого дня | ✅ Вынесенные сервисы независимы, оставшиеся модули пока живут в монолите |
| Изоляция данных: своя БД, нет прямого доступа к чужой | ❌ Общая PostgreSQL — изоляция данных отсутствует | ✅ Сразу у каждого сервиса своя БД, прямых межбазовых запросов нет | ✅ Достигается по мере выноса: у сервиса своя БД, остальное временно на shared-БД |
| Постепенность миграции / migration risk | ❌ Риска нет, но исходные проблемы связанности и общей БД сохраняются | ❌ Максимальный риск: интеграции, данные, деплой и откат нужно решить одномоментно | ✅ Риск управляемый: изменения малыми инкрементами, каждый шаг обратим |
| Непрерывность сценария бронирования | ✅ Сценарий работает, но архитектура не развивается | ❌ Риск простоя и регрессий на время переключения и миграции данных | ✅ Сценарий сохраняется: монолит работает, пока трафик переключается по canary |
| Переключение трафика и rollback | ❌ Неприменимо: переключать и откатывать нечего | ❌ Практически отсутствует: откат означает возврат всего релиза | ✅ Есть traffic splitting, canary и откат на уровне отдельного сервиса |
| Новая функциональность только в сервисах | ❌ Фичи продолжают добавляться в общий модуль монолита | ✅ Вся новая разработка идёт в независимых сервисах | ✅ Новые фичи идут в вынесенные сервисы, монолит только затухает |
| Наблюдаемость: метрики, логи, трейсы | ⚠️ Метрики и логи есть у монолита, но трейс через границы сервисов не выстроен | ✅ Единый стек метрик, логов и распределённых трейсов настраивается сразу | ✅ Обеспечивается: корреляция и трейсы проходят через Gateway, BFF и сервисы |
| Health/readiness checks и graceful shutdown | ⚠️ Health монолита не отражает состояние отдельных модулей | ✅ Каждый сервис получает собственные checks и graceful shutdown | ✅ Обязательные checks и graceful shutdown для каждого вынесенного сервиса |
| Операционная сложность и стоимость владения | ✅ Самая низкая: одна инфраструктура и один деплой | ⚠️ Высокая: сразу нужны mesh, CI/CD, observability и БД на каждый сервис | ⚠️ Растёт постепенно: инфраструктура вводится по мере выноса сервисов |
| Latency и число сетевых вызовов | ✅ Межсервисных вызовов нет — минимальная задержка | ⚠️ Много сетевых вызовов сразу, нужны timeouts, retries, circuit breakers | ⚠️ Вызовы растут пошагово и компенсируются mesh, pooling и caching |
| Скорость получения бизнес-ценности | ❌ Ценности не даёт: только консервирует текущие проблемы | ❌ Долго до результата: ценность появляется лишь после полного переписывания | ✅ Быстрые инкременты: первый вынесенный сервис даёт эффект рано |

**Резюме** 

Выбранный поэтапный вариант Strangler Fig + API Gateway + GraphQL BFF закрывает все НФТ при контролируемом риске и возможности поэтапного отката.

**Недостатки, ограничения, риски**

| Риск | Последствие | Митигация |
| :- | :- | :- |
| Множество сетевых вызовов| Дополнительная задержка и новые точки отказа | Timeouts, retries, circuit breakers, tracing |
| Shared DB останется надолго | Сервисы останутся связанными через данные | Явное владение и постепенное разделение БД |
| Рост числа сервисов | Рост операционной сложности | CI/CD, service mesh, observability |
| Ошибки маршрутизации при миграции | Запросы могут попасть в неправильную реализацию | Canary/traffic splitting и rollback |
